# Módulo — i18n (Tradução / Multi-idioma)

## Propósito
Infraestrutura para o VOXEL PACS suportar pt_BR (padrão)/en/es, com idioma configurável por Negócio (tenant). Criada em 2026-07-15 — antes disso não existia nenhum mecanismo de tradução no projeto (só `<html lang="pt-BR">` estático em vários layouts).

## Arquivos principais
| Arquivo | Papel |
|---|---|
| `lang/pt_BR.php`, `lang/en.php`, `lang/es.php` | Arrays de tradução, mesma chave nos 3 (ver `diagnostics/i18n.md` para o script de paridade) |
| `app/Core/Translator.php` | Resolve idioma ativo, lê/cacheia os arrays, fallback pt_BR se chave/idioma faltando |
| `app/helpers.php` | Função global `t('chave')`, carregada no `bootstrap.php` |
| `app/Middlewares/TenantMiddleware.php` | Chama `Translator::setLocale($tenant->idioma_padrao)` uma vez por request, junto com `TenantContext::set()` |
| `database/migrations/2026-07-15_bi_tenants_idioma.sql` | Coluna `bi_tenants.idioma_padrao` ENUM('pt_BR','en','es') DEFAULT 'pt_BR', idempotente via `vp_add_col` |
| `app/Views/platform/negocios/form.php` | Campo de seleção do idioma padrão do Negócio (aba "Plano") |
| `app/Controllers/Platform/NegociosController.php` | `store()`/`update()` persistem `idioma_padrao`, com whitelist contra `Translator::SUPPORTED` |

## Dependências
- Depende de: `TenantContext`/`TenantMiddleware` (para saber qual tenant, logo qual idioma, está ativo na requisição) — ver `modules/tenants.md`.
- Consumido por: qualquer view que chame `t()`. Hoje só `app/Views/platform/negocios/index.php`.
- Ver `architecture/dependencias.md` para o grafo completo.

## Padrões seguidos
Ver `patterns/padrao-i18n.md` — convenção de chave, como adicionar uma chave nova, regra de que toda tela nova/alterada já nasce nos 3 idiomas (Modo Enterprise, `SKILL.md`).

## Escopo desta fase (2026-07-15) — decisões conscientes, não gaps esquecidos

- **Idioma só por Negócio, sem override por usuário individual.** `bi_users` não ganhou coluna de idioma. Se um caso de uso real pedir isso depois, é feature nova (coluna em `bi_users` + lógica de precedência usuário > tenant > pt_BR), não presumir que já existe.
- **Só 1 tela migrada para `t()`** — `app/Views/platform/negocios/index.php`, escolhida como piloto por ser pequena e já bem entendida (mexemos nela em tarefas recentes de multi-tenant/impersonação). Não é a tela mais usada do sistema (essa é a Worklist, `app/Views/estudos/index.php`) — a prioridade de migração das próximas telas deve ser decidida numa tarefa futura, não presumida aqui.
- **Mensagens flash do Controller não migradas.** `NegociosController::store()/update()/suspend()` ainda gravam `$_SESSION['success']`/`$_SESSION['error']` com string PT hardcoded (ex: "Negócio criado com sucesso!"). A view já exibe esse conteúdo via `t()`-free `htmlspecialchars($_SESSION['success'])` — funciona, mas não traduz. Fora do escopo desta tarefa (pilot era só a view de listagem); migrar isso é a extensão natural quando `form.php`/`store()`/`update()` forem migrados.

## Riscos / pontos frágeis conhecidos
- `Tenant::findById()` (`app/Models/Tenant.php`) usa `INNER JOIN bi_plans` — já documentado como risco em `architecture/auth-e-permissoes.md`/`modules/tenants.md` (afeta impersonação); o mesmo risco se aplica aqui: se `findById()` retornar `null` por um plano ausente, `Translator::setLocale()` nunca é chamado naquele request, e a página cai no fallback pt_BR silenciosamente (comportamento seguro, mas pode confundir um tenant que configurou outro idioma).
- Migrar uma tela para `t()` sem rodar o script de paridade de `diagnostics/i18n.md` é o erro mais fácil de cometer — uma chave nova só em `pt_BR.php` não quebra nada visivelmente (cai no próprio fallback), então o esquecimento não aparece sozinho em teste manual rápido.
